# SP2 design review 04: the security lens (first draft of the plan, 2026-10-05, at b69ff0c)

VERDICT: No blocker through the security lens: the constant 127.0.0.1 bind with exclusive binding, the exact Host check, the lookup by listing, the '<'-escaped ASCII JSON block and --open off by default are right and I found nothing wrong with them. But everything the plan added after the survey (PNG frame upload, ffmpeg, the framed scene page, the hash hook) has no stated rule, and two survey rules contradict the plan's own design (the JSON-only 64 KiB guard refuses the frame route; the survey's X-Frame-Options DENY and its CSP both block the scene iframe, verified in Chrome). The most important change is to replace the one guard sentence in 4.6 with a per-route policy table (method, content type, body cap, Sec-Fetch-Site, frame and CSP headers) covering the frame route and the scene page, and to make that table a tested gate of A4 and A6v; I would also cut GET /api/scene, GET /api/videos/&lt;id&gt;/file and POST /api/validate, and cap hard or cut the in-app GIF.

## 1. [major] The request guard of 4.6 refuses the video routes of 4.9, and nothing says what applies to them instead

CLAIM: As written every POST must be application/json and at most 64 KiB, so the PNG frame route (image/png, up to 4 MiB) cannot work, and the exception the implementer must invent is exactly where a cross-site post can get in.

EVIDENCE: Plan 4.6 ("POST needs application/json, one Content-Length of at most 64 KiB, strict JSON, an object at top level") against plan 4.9 ("POST /api/videos/<id>/frames (PNG body, in order)", "4 MiB per frame"). Measured with headless Chrome against two scratch loopback servers (C:/Users/rahul/AppData/Local/Temp/claude/D--DEV-ClaudeProjects-SpaceRocketOptimization/6999a833-8705-4f59-babb-7d35feacc46d/scratchpad/a0/review/sec_probe3.py): a page on another origin doing fetch(url, {method:'POST', mode:'no-cors', body: <Blob of type image/png>}) reaches the server with its own Origin and with NO Content-Type header (the browser drops the non-safelisted type); a text/plain post arrives as text/plain; a cors-mode post that sets image/png or application/json is preflighted (OPTIONS, which the app answers 501). So a frame route that accepts a missing or any content type has Origin as its only check; one that demands exactly image/png has two.

CHANGE: Replace the POST sentence of 4.6 with a route table applied before any body byte is read (order: Host, Origin, Sec-Fetch-Site, method and route, Content-Type, Content-Length): (a) POST /api/launches, /api/videos, /api/videos/<id>/finish: media type exactly application/json, one Content-Length <= 64 KiB, strict JSON object (finish sends {}); (b) POST /api/videos/<id>/frames/<n>: media type exactly image/png (no parameters), one Content-Length <= 4 MiB and <= the job's remaining byte budget, <id> an unguessable token of an open job; (c) every other POST path 404; any other content type 415 and an over-limit length 413, both without reading the body; Transfer-Encoding 400. Add raw-socket tests for the frame route: no Content-Type with a foreign Origin -> 403; no Origin and no Content-Type -> 415; text/plain -> 415; image/png with a foreign Origin -> 403; 4 MiB + 1 announced -> 413 at once; unknown id -> 404; each leaves the job unchanged.

## 2. [major] The survey's frame headers and CSP block the scene iframe of D-SP2-22; the plan names no header set and no CSP for any of its three pages

CLAIM: Plan 4.6 says only "fixed safety headers on every response"; the only concrete list (survey 07) breaks the app's own iframe twice, and the scene page, the exported page and the video capture have no policy at all.

EVIDENCE: Survey 07 section 3.2 and its prototype (m07_safety.py lines 212-218) send X-Frame-Options: DENY on every response; survey 3.4 gives a CSP for GET / only, with default-src 'none' and no frame-src. D-SP2-22 frames /scene/... from /. Measured in headless Chrome (review/sec_probe3.py): a same-origin iframe whose response carries X-Frame-Options: DENY is blocked (SAMEORIGIN loads), and under the survey's CSP the app page's own iframes are not even requested. Exit criteria 12 and 15 ("no request off the machine", "no network request") have nothing enforcing them. Measured (review/sec_probe4.py): a meta CSP with default-src 'none' on a standalone file page lets the page run and read its application/json block and refuses fetch; with script-src 'unsafe-inline' an inline handler injected through innerHTML runs, with script-src 'sha256-<hash of the script>' it does not and the page still works. D-SP2-30 has the scene page itself post frames, which a request-free scene policy forbids. site/templates/replay-frame.html inserts a same-origin <img> and icon link into framed pages, so an exported page's policy needs img-src 'self'.

CHANGE: Write the headers into 4.6. Every response: X-Content-Type-Options: nosniff; Cache-Control: no-store; Referrer-Policy: no-referrer; Cross-Origin-Resource-Policy: same-origin; Cross-Origin-Opener-Policy: same-origin; no Access-Control-* header. GET /: X-Frame-Options: DENY and CSP "default-src 'none'; script-src 'sha256-<app script>'; style-src 'unsafe-inline'; img-src 'self' data:; connect-src 'self'; frame-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'". GET /scene/...: X-Frame-Options: SAMEORIGIN and CSP "default-src 'none'; script-src 'sha256-<scene script>'; style-src 'unsafe-inline'; img-src 'self' data:; base-uri 'none'; form-action 'none'; frame-ancestors 'self'" (no connect-src: the scene page can make no request). Every other response: X-Frame-Options: DENY and CSP "default-src 'none'; frame-ancestors 'none'". Exported page: scene.render_page writes the same scene policy without frame-ancestors as a <meta http-equiv> (hash computed at render); the A8 frame rule of site/build.py must not edit the script. Change D-SP2-30 so the app page drives the capture: it calls launchsimScene.captureFrame(t) on the same-origin frame, receives the PNG blob and posts it itself; the video button lives in app.html, so the exported page has none by construction and D-SP2-22's "the page in the app is the exported page" stays literally true. Tests: header table per route; the framed scene loads in the QA browser; a framed / from another origin does not.

## 3. [major] Cross-site GETs pass the guard and can make the server build scene payloads without bound; the survey's Sec-Fetch-Site rule was dropped

CLAIM: "Origin absent or the app's own" lets any web page (or a page on another loopback port) issue GETs that reach the handlers, and each distinct /scene URL costs a payload build that the plan neither caches nor bounds.

EVIDENCE: Plan 4.6 guard; survey 07 section 3.2 had a Sec-Fetch-Site rule (for POST only) that 4.6 does not carry. Measured in Chrome (review/sec_probe3.py): cross-origin <img>, fetch(no-cors) and <iframe> GETs arrive with no Origin header; Sec-Fetch-Site is same-site from another port on 127.0.0.1 and cross-site from a localhost page; the iframe GET is served before the browser applies X-Frame-Options. The port is fixed (8765, D-SP2-29) and the experiment names, timestamps and run names are public (16 tracked results/*/*/summary.md in the public repository). results/silo_offload_2d/20261003T112934Z has 19 run folders with a timeseries.csv, so 99,199 ordered selections of 1 to 4 runs are valid /scene URLs for that one directory; each reads up to four 3.6 MB CSVs (about 50 ms each in pandas, survey 07 section 1.3) and runs the builder's every-row checks and vacuum coasts (D-SP2-16, D-SP2-19) in a handler thread sharing the GIL with a launch. The plan has no payload cache; the survey's suggestion (07 section 6: bytes cached "per directory and selection") is unbounded. GET /scene and GET /api/scene deliver the same payload twice.

CHANGE: Add to the guard: on every request except GET /, when Sec-Fetch-Site is present it must be same-origin or none (a typed or bookmarked address, headless QA), else 403 before routing; GET / stays open to a cross-site navigation so a link from the manual works. Add to 4.6: a scene selection is 1 to 4 distinct runs; one payload build at a time (a lock; a second request for the same key waits and reuses); an LRU of at most 8 encoded payloads keyed by directory, selection and the mtime of metrics.json. Cut GET /api/scene/...: the page embeds its payload and tests call the builder in Python. Tests: Sec-Fetch-Site same-site and cross-site on GET /scene/..., /api/results and /api/job -> 403; GET / with cross-site -> 200; two concurrent identical scene requests build once; a ninth selection evicts the oldest.

## 4. [major] No DOM-insertion rule for scene.html and app.html, while disk strings, refusal text and FAILED.txt lines reach both

CLAIM: The plan fixes how JSON is embedded but not how strings are put into the page, and its model (the replay template) relies on remembering esc() at every innerHTML site; the strings the app will show include echoed input and text read from results directories.

EVIDENCE: Plan 4.4-4.7 contain no rule; D-SP2-21 takes replay.html as the model, which assigns innerHTML at lines 463, 492, 537, 556 and 566 with esc() (225-227) applied by hand. Strings bound for the pages: the 422 message "the simulator's message condensed to one line" (plan 4.6), and pydantic's text carries the input and an external URL (s03_refusals_out.txt lines 13-14: "[type=value_error, input_value={'model': 'constant_accel..., input_type=dict]" then "For further information visit https://errors.pydantic.dev/2.13/v/value_error"); offload.caveats "word for word" (plan 4.4); run names, flags and statuses from metrics.json; a recorded metrics.json already holds '&' in a string ("Espace & Exploration No.39 ...", results/silo_offload_2d/20261003T112934Z); a results directory named x' onmouseover='1 is a legal Windows name. Phase file 5.7 (line 648) lists "an invalid name" as a refusal the form must produce, while plan 4.7 has no name field and D-SP2-31 admits only booleans and numbers, so whether a name string travels in the request is undecided; results_io.check_name echoes the whole name with !r (results_io.py 213-225). Measured (review/sec_probe4.py): under script-src 'unsafe-inline' an inline handler injected through innerHTML runs.

CHANGE: Add to 4.5 and 4.6: (1) neither new template assigns innerHTML or outerHTML, calls insertAdjacentHTML or document.write with anything but a string literal; every payload or API value goes in with textContent or createElement; URLs are built with encodeURIComponent per segment; a fast test scans both templates for those sinks against a short allow-list of literal-only lines. (2) Rendering substitutes the JSON data token and nothing else: no server-side string enters the HTML. (3) Refusal text is built from ValidationError.errors(include_url=False, include_input=False) (loc and msg) or the first line of a ValueError, one line, at most 300 characters, never str(exc). (4) D-SP2-31 states that the request carries no run, case or experiment name: the server derives them from the enumerated site, preset and mode; choice fields accept only values of a fixed enumeration; a refusal never echoes an unknown key or value longer than 40 characters; the "invalid name" refusal of 5.7 is logged as not reachable from the form. (5) An injection test: a synthetic directory whose run label, caveat, flag and FAILED.txt line contain <img src=x onerror=window.__x=1> and </script><script>window.__x=1</script> is rendered as a scene page and as results-panel data, loaded in the QA headless browser, and window.__x is undefined with the text shown literally. The hash-based script-src of the header finding is the second layer.

## 5. [major] ffmpeg: how it is found, invoked, timed out and cleaned up is not specified, and on Windows a bare-name lookup runs a file from the working directory

CLAIM: The plan says only that frames are piped to ffmpeg; the lookup, the argument list, stderr handling, a hung or dead encoder, an abandoned capture and concurrency with a launch are all open, and the default lookup on Windows prefers the directory the server was started in.

EVIDENCE: Plan D-SP2-30 and 4.9 ("pipes them to ffmpeg", "MP4 needs ffmpeg (a clear message without it)", "one video at a time"). Measured (review/sec_probe2.py, run with the normal Windows environment, that is with NoDefaultCurrentDirectoryInExePath unset): with a file ffmpeg.exe in the current directory, shutil.which("ffmpeg") returns '.\\ffmpeg.EXE' and subprocess.run(["ffmpeg", "-version"]) (list form, no shell) runs that file instead of the installed ffmpeg 8.1. The agent harness sets that variable, and with it the planted file is not found, so a test run from a session like this one passes without testing the default. The existing animate path uses matplotlib's bare name (rcParams animation.ffmpeg_path = 'ffmpeg'; plots.py 1867). The same plan makes the working directory the place videos are written. "One video at a time" with no timeout means a closed tab leaves the slot taken and an ffmpeg process alive until the server stops. D-SP2-09's measurement covers 74-byte polls and 1 MB payloads during a solve, not 1,800 uploads of up to 4 MiB.

CHANGE: Add to 4.9: ffmpeg is resolved once at server start with shutil.which over PATH entries that are absolute; a candidate whose resolved folder is the working directory, the repository or the results root is rejected; the absolute path is stored and printed in the start banner. Invocation, list form, shell=False, stdin=PIPE, stdout=DEVNULL, stderr to a file in the job's temp folder, cwd = that folder: [ffmpeg, -hide_banner, -loglevel error, -nostats, -f image2pipe, -c:v png, -framerate <fps>, -i pipe:0, -frames:v <n>, -an, -c:v h264, -pix_fmt yuv420p, -crf <MP4_CRF>, -movflags +faststart, -n, <temp output>]; the forced input format and decoder mean uploaded bytes are never format-probed. Lifecycle: one writer thread per job with a queue of 2 frames; a frame POST waits at most 10 s for room, else 503; no frame for 30 s, a pipe write blocked for 30 s, or finish not complete in 120 s -> proc.kill(), temp folder removed (tempfile.mkdtemp, outside the repository and the results root), slot freed, job failed with the last 300 characters of stderr; the same clean-up on Ctrl+C. POST /api/videos answers 409 while a launch runs and POST /api/launches answers 409 while a video job is open. Tests in A6v's gate: a fake encoder passed in as the resolved path that never reads stdin, one that exits early, one that floods stderr; an abandoned job frees the slot; a subprocess test with the variable cleared and an ffmpeg.bat planted in the working directory shows the server does not select it.

## 6. [major] Uploaded frames: no format, pixel-size or total-size rule; the limits as written admit about 7 GiB per job and Pillow would sniff 43 formats

CLAIM: "1,800 frames, 4 MiB per frame" bounds neither what a frame decodes to nor what the server holds for the GIF, and the plan does not say that a frame must be a PNG of the job's size before Pillow or ffmpeg sees it.

EVIDENCE: Plan 4.9. 1,800 x 4 MiB is about 7 GiB of accepted bytes per job; the GIF path (Pillow) needs every frame before or while writing. Measured with the installed Pillow 12.3.0 (review/sec_probe1.py): Image.open(body) identified BMP and GIF bodies and tries 43 formats including EPS unless formats=["PNG"] is passed (then UnidentifiedImageError); a 73-byte PNG whose IHDR declares 12,000 x 12,000 px opens with only a DecompressionBombWarning (the error starts above 178,956,970 px), which is 412 MiB of RGB on decode; an all-black 8,000 x 8,000 PNG is 187 kB, so the 4 MiB cap does not bound decode cost. The request fields "fps, seconds, width" have no ranges and the frame height is not fixed anywhere.

CHANGE: Add to 4.9: POST /api/videos fixes the job: format in {mp4, gif}; fps from a list (10, 15, 20, 25, 30); frames = fps x seconds as integers, 1 to 1,800; width from a list (for example 960, 1280, 1920), height derived by the server from the composite's fixed aspect, both even; a total byte budget of 512 MiB. Every frame body is checked before it is piped or decoded: the 8-byte PNG signature, IHDR as first chunk with exactly the job's width and height, bit depth 8, colour type 2 or 6, no interlace, IEND as last chunk; otherwise 422 and the job is unchanged. Pillow opens a frame only with Image.open(buf, formats=["PNG"]) and compares im.size before load(). GIF: at most 300 frames and width at most 960, each frame quantised on arrival and held palettised under a 256 MiB cap; MP4 frames are never stored. Tests: a BMP body, a PNG of another size, a PNG declaring 12,000 x 12,000, frame 1,801, and the byte budget, each refused without ending the job. Simplification worth offering the user: cut the in-app GIF (exit criterion 15 would ask for MP4 only); the server then never decodes an upload in its own process.

## 7. [major] Nothing in the gates or exit criteria measures the cross-site guard, and survey rules were dropped from 4.6 without saying so

CLAIM: R11 is resolved by "a reviewer checks it in A4"; A4's gate and the 15 exit criteria test the bind and the form refusals but not Host, Origin, Content-Type, Sec-Fetch-Site, traversal or body limits, so the phase can close with the guard untested.

EVIDENCE: Plan section 5, A4 gate ("only 127.0.0.1 bound and a second server on the port fails; no client path opened; refusals write nothing; ..."); exit criteria 1 and 4; phase file risk R11. Survey 07 section 3.2 proved 38 raw-socket cases on a prototype, but the plan does not adopt them as a test. Rules of survey 3.1-3.2 absent from plan 4.6: handler timeout (StreamRequestHandler.timeout is None by default: an idle connection parks a thread for ever), default_request_version = HTTP/1.0 (a two-word request line otherwise gets a body with no status line or headers), Transfer-Encoding refused, non-empty query refused, absolute-form target refused, server_bind without getfqdn, the lock around "check idle and start". Measured (review/sec_probe1.py and a follow-up): a 60,000-byte body of nested arrays raises RecursionError, which the prototype's except (UnicodeDecodeError, ValueError) at m07_safety.py 268-271 does not catch. The residual risk the survey accepts (any process or other user of the machine can call the API on 127.0.0.1, and with 4.9 can feed bytes to ffmpeg and Pillow) is not stated in plan section 8.

CHANGE: 4.6: "the server applies every rule of survey 07 sections 3.1 and 3.2, with the changes listed here", naming handler timeout 30 s, default_request_version HTTP/1.0, Transfer-Encoding 400, query string 400, absolute-form 400, RecursionError mapped to 400, the 409 busy check under one lock before the resolve. A4 gate, add: "the raw-socket guard table passes in the fast suite: the survey's 38 cases plus Sec-Fetch-Site same-site and cross-site on GET and POST, the nested-JSON body, two simultaneous launch POSTs giving exactly one 202, the Host allow-list built from the bound port with --port 0, and no command option that changes the bind address". A6v gate, add the frame-route cases. New exit criterion 16: "Requests from another origin are refused: a page on another loopback port and a page on another host cannot start a launch, post a frame or make the server build a scene; checked by the guard table in the fast suite and once with a real browser, recorded in the demo." Section 8: state the accepted risk (other local processes and users) in one line, and repeat it in the manual chapter.

## 8. [major] Video routes: guessable ids, no frame index, an output name taken from file content, and "never overwriting" that the shared rule does not provide

CLAIM: Four details of 4.9 are undefined or contradicted by the code the plan points to, and the download route duplicates a file the server has already written.

EVIDENCE: Plan 4.9: <id> is unspecified (the launch job id of survey 07 section 6 is a counter starting at 1); "PNG body, in order" has no index, so a retried or lost POST silently shifts the film while A6v's gate counts frames; the file is written "under the shared output-path rule, never overwriting", but that rule (replay.check_replay_out, replay.py 1222-1234) checks the suffix, the results tree and the folder, not existence, and write_replay_page overwrites (replay.py 1243, write_text); its default name is built from metrics.json's experiment and timestamp_utc fields (replay.py 1213-1217; plots.py 984-990), that is from file content, sanitised by plot_stem (plots.py 90-96) but with no length limit. GET /api/videos/<id>/file serves a second copy of a file already in the working directory, with no Range support in BaseHTTPRequestHandler and a body that can be hundreds of MB.

CHANGE: 4.9: <id> is secrets.token_urlsafe(16) returned by the create call and looked up in an in-memory table, never part of a path. Frames go to POST /api/videos/<id>/frames/<n>; n must be the next index (409 otherwise). The output name uses the experiment and timestamp of the server's own listing (already validated), not metrics.json. The encoder writes into the job's temp folder; on finish the server reserves the final name with open(path, "xb"), trying -2, -3, ... as make_run_dir does, then os.replace()s the temp file onto it; a failed job removes its reservation; state this as a new rule of run_data.check_output for the video only, with a test that an existing file is kept. Cut GET /api/videos/<id>/file: finish returns the file name and folder, shown as text. If the download is kept: token id only, streamed in 64 KiB chunks, Content-Disposition: attachment, a fixed type per format.

## 9. [minor] The run browser has no state for a directory whose files do not parse, and reads have no size or link rule

CLAIM: One truncated or hostile metrics.json can turn GET /api/results into a 500 for the whole listing, and the readers follow junctions and read files whole.

EVIDENCE: Plan 4.6 lists four states (running, complete, failed, incomplete) and exit criterion 8 four refused kinds. The readers at HEAD (replay.py 148-154, plots.py 627-633) call json.load with no size limit and let JSONDecodeError and RecursionError through. A hard stop during write_run can leave a truncated last file (survey 07 section 4.1), so this is an expected state. animation_run_names (plots.py 651) accepts any subfolder with a timeseries.csv, including a junction; Path.is_junction exists on this Python (checked). FAILED.txt is a full traceback (results_io.py 575-578) whose last line for a pydantic error is the "For further information visit https://errors.pydantic.dev/..." line, so "the marker's last line" (survey 07 section 4.4) is the wrong line there.

CHANGE: 4.6: a fifth state "unreadable" (fixed text; the directory stays listed); /api/results handles each directory separately and lists only entries whose names pass check_name and the timestamp pattern, with a count of the others; the app's readers refuse metrics.json or resolved_config.yaml over 16 MiB and a CSV over 64 MiB, and skip a run folder or file that is a symlink or junction or resolves outside the results root; FAILED.txt: read at most the last 8 KiB and show the last line that does not start with a blank and is not the pydantic URL line, cut to 200 characters. Add to exit criterion 8: a truncated metrics.json, a 60 kB nested JSON and a directory named x' onmouseover='1 leave the listing at 200 and the form usable.

## 10. [minor] The URL hash (#t, #theme, #qa) has no parsing rule, and the exported page will sit on the public Pages origin

CLAIM: The plan names the hash keys but not how they are parsed or written, and exit criterion 13 publishes an exported scene in the gallery, so a crafted link reaches that code on the project's public site.

EVIDENCE: Plan 4.5 ("A hash such as #t=12.5&theme=dark opens a fixed frame; #qa=<times> writes the states into the page") and exit criterion 13 ("gallery with an exported scene"). The states written for #qa include event names from the payload. A page that opened the scene keeps a handle and can re-set its fragment.

CHANGE: 4.5: a pure parseHash(text) in the template: t is a finite number clamped to the data's time range; theme is exactly light or dark; qa is at most 200 comma-separated finite numbers; any other key or value is ignored. The #qa output is JSON.stringify written with textContent into one fixed element. Nothing from the hash is used as HTML, a URL, a selector or a style value. A node test runs parseHash on t=<img src=x onerror=1>, theme="><script>, qa=1,2,<svg onload=1>, t=1e999, t=NaN and a qa list of 1,000,000 entries.

## 11. [minor] "Strict JSON" does not stop 1e400, a 400-digit integer or true in a number field

CLAIM: The guard's NaN and Infinity refusal works on the literals only; non-finite and oversized numbers still reach the form parser, whose finiteness check can itself raise.

EVIDENCE: Measured in this environment: json.loads('{"x": 1e400}', parse_constant=<raise>) returns {'x': inf}; json.loads of a 401-digit integer returns an int and math.isfinite on it raises OverflowError ("int too large to convert to float"); isinstance(True, int) is True. D-SP2-31 and exit criterion 4 promise that non-finite numbers and booleans in number fields are refused by the app.

CHANGE: 4.7: the parser accepts a number only when type(v) is int or float (never bool), bounds an int's magnitude before converting, and then requires math.isfinite; any failure is the one-line 422, never a 500. Add to the tests of exit criterion 4: 1e400, -1e400, a 400-digit integer, true and "3" in a number field, each refused with nothing written.

## 12. [minor] The run-selection path segment has no decoding rule

CLAIM: "One percent-encoded path segment" leaves open when the path is split and how often it is decoded, which is where an encoded slash or a double decode slips in.

EVIDENCE: Plan 4.6. NAME_PATTERN (results_io.py 186) allows only [A-Za-z0-9_.+-], none of which needs encoding in a path segment; the survey prototype splits the raw path and never decodes (m07_safety.py 292-293); JavaScript's encodeURIComponent turns '+' into %2B, and parse_qs turns a raw '+' into a space (survey 07 section 3.2), so both spellings will occur.

CHANGE: 4.6: the request path is split on '/' before any decoding; each segment is decoded once with urllib.parse.unquote (never unquote_plus); a decoded segment containing '/', '\\', '%', a control or a non-ASCII character is 400; a selection is 1 to 4 distinct names joined by ',', each a member of the directory's own run list. Tests: raw '+' stays '+'; %2B gives '+'; %2F, %5C, %00 and %252e%252e are refused; five runs and a repeated run give 422.

## 13. [minor] POST /api/validate duplicates the launch route's refusal path

CLAIM: A second route that runs the same parser and resolve doubles the refusal surface that exit criterion 4 must test and gives nothing the launch route does not.

EVIDENCE: Plan 4.6: the resolve, name check and preflight "run in the request (9 ms), so a refusal writes nothing" on POST /api/launches; POST /api/validate is listed with no stated use in 4.7.

CHANGE: Cut POST /api/validate, or make it the launch route with "dry_run": true in the same JSON body (same parser, same messages, 200 with the refusal or the resolved summary, never a job). State which in 4.6 and test the refusals of criterion 4 on the one route.
