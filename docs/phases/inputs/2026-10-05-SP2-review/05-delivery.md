## 6. [major] Thread, socket and subprocess leaks will fail unrelated tests under filterwarnings=error

CLAIM: The plan adds a threaded server, a worker thread and an ffmpeg pipe to a suite where any ResourceWarning or unhandled thread exception is raised as an error in whichever test runs next, and states no discipline for it.

EVIDENCE: pyproject.toml line 46: `filterwarnings = ["error"]`. Installed pytest 9.1.1, .venv/Lib/site-packages/_pytest/unraisableexception.py lines 47-81 and 176-187: unraisable exceptions (a ResourceWarning turned into an error inside a finaliser) are queued and re-raised as PytestUnraisableExceptionWarning in the setup, call or teardown of the test then running; threadexception.py lines 40-72 does the same for an exception that escapes a thread. Survey 08's header says this was 'Not verified ... to be checked by the first server test'. Plan sections 4.6, 4.9 and 7 do not mention it. An abandoned video (the page closed before /finish) leaves a `subprocess.Popen` whose finaliser warns 'subprocess is still running'. A baseline cache held in a module global would also leak between tests: in tmp directories every test's server-start git state is `no-git`, so the keys collide.

CHANGE: Add to 4.6: 'The cache, the job state and the video session belong to the server object, never to a module global. The server is a context manager: exit calls shutdown() from another thread, then server_close(), then joins the worker with a timeout. Test fixtures use it with poll_interval 0.02; every http.client connection is closed in a finally; a test that starts a job waits for its end before teardown. A video session closes ffmpeg's stdin and waits in a finally, and is reaped after an idle timeout or when the next session starts.' Add one fast test that opens and closes a server and a video session, then calls gc.collect() inside `warnings.catch_warnings(record=True)` and asserts no ResourceWarning.

## 7. [major] The gate 'an interrupted job leaves FAILED.txt' cannot be exercised as written on Windows

CLAIM: An agent or a test cannot deliver Ctrl+C to a running `launchsim app`, and Ctrl+Break kills the process with no clean-up unless a SIGBREAK handler is installed, which the plan does not include.

EVIDENCE: Plan lines 249-250 and A4's gate (line 339). Survey 07 section 4.2: 'A real console Ctrl+C was not sent'; section 4.3 item 5 lists the SIGBREAK handler as optional. Probe run for this review (dl_ctrl_parent.py and dl_ctrl_child.py in the review scratch folder, Python 3.12 from the project environment): CTRL_C_EVENT sent to a child started with CREATE_NEW_PROCESS_GROUP was ignored (child still running after 4 s, no marker); CTRL_BREAK_EVENT with no handler ended the child at once with exit code 3221225786 (0xC000013A) and no marker; CTRL_BREAK_EVENT with `signal.signal(signal.SIGBREAK, signal.default_int_handler)` raised KeyboardInterrupt in the child, which wrote its marker and exited 0 in 0.13 s. So a user who presses Ctrl+Break or a harness that stops the server gets a directory with neither file.

CHANGE: In 4.6: '`command_app` installs `signal.signal(signal.SIGBREAK, signal.default_int_handler)` on Windows, so Ctrl+Break is handled like Ctrl+C.' In A4b's tests: (1) fast: the stop routine called directly with a fake active job writes FAILED.txt, and writes none when the job finished during the join; (2) one subprocess test: start `python -m launchsim app --port 0 --results-root <tmp>` with CREATE_NEW_PROCESS_GROUP and a stub basis, post a launch, send CTRL_BREAK_EVENT, assert exit code 0, the 'stopped' line and FAILED.txt. Reword the gate: 'an interrupted job (Ctrl+Break in the subprocess test; Ctrl+C by hand in the demo) leaves FAILED.txt; a killed process leaves an incomplete directory, shown as such'.
